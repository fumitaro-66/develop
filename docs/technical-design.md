# 技術設計書

## 1. 技術スタック
- 言語：Swift
- UI：SwiftUI
- ローカル永続化：SwiftData
- 対象：iPhone、iOS 17以降
- 外部サーバー・アカウント・クラウド同期：なし
- バックアップ形式：JSON
- ソース管理：Git
- 開発ツール：Claude Code、Xcode、VS Code

## 2. レイヤー方針
実際のXcodeプロジェクト構成を確認したうえで、少なくとも次の責務を分離する。
- **UI層**：SwiftUI画面、入力、表示、ユーザー操作
- **ドメイン／サービス層**：数量計算、材料名正規化、調味料除外、週コピー、入力検証
- **データ層**：SwiftDataによる読み書き、トランザクション的操作
- **バックアップ層**：JSONエンコード／デコード、検証、ファイル入出力

数量計算ロジックはViewの中に直接埋め込まず、ユニットテスト可能な独立した型またはサービスにする。

## 3. エラー処理
- 保存失敗：エラー表示、入力を保持、再試行。部分保存を避ける。
- 起動時読み込み失敗：空データとして初期化しない。再試行とバックアップ復元を案内する。
- レシピ削除失敗：レシピ・材料・献立登録を一括でロールバックする。
- 買い物リスト再計算失敗：直前の正常なリストとユーザー状態を保持し、古い可能性を表示して再試行する。
- バックアップ作成失敗：アプリデータを変更せず、エラーと再試行を表示する。
- 復元失敗：現行データを変更しない。形式・バージョン・整合性エラーを分かる形で表示する。
- 調味料設定保存失敗：旧設定を保持する。
- 保存されている数量の不正：推測で補正せず、保存済みデータを変更しない。買い物リストでは再計算の失敗として扱い、レシピ編集画面では該当する材料の行にエラーを表示して再入力を促す（data-design 3.1、screen-design §4）。

エラーを握りつぶさず、開発時には原因を追跡できるようにする。個人情報やレシピ内容を外部へ送信するログ機能は作らない。

## 4. SwiftData実装時の注意
- プロジェクトのDeployment Targetと利用可能なSDKを確認して実装する。
- 関連モデルの削除や復元は、整合性を保つ方法を採用する。
- 保存処理の失敗時にUIと永続化データが不整合にならないようにする。
- SwiftDataの制約により論理設計を調整する必要がある場合、ユーザーに理由・影響・案を説明して承認を得る。
- アプリ起動時にモデル読み込みが失敗した際、空のModelContainerで既存データを上書きしない。

### 4.1 確認済みの事実と未検証の事項
確認した環境：Xcode 15.2（iOS 17.2 SDK）、macOS 13.7.8、iPhone 15シミュレーター（iOS 17.2）。iOS 17シミュレーターでの動作確認は D-006、D-007、D-008 を実施済みで、ほかの項目は未実施である。実機（iOS 27）での確認はまだ行っていない。

「APIが存在する（SDKに宣言がある）」ことと、「そのAPIが期待どおりに動作する」ことは区別する。前者は確認済みである。後者は、確認済みの事実の表で動作を確認したと明記した項目（D-006、D-007、D-008）を除き、未検証である。

### 4.2 一括処理（トランザクション）の方針
以下は設計方針である。この方針で一括性が守られるかは4.1の未検証事項であり、確認するまで保証された仕様として扱わない。
- 一括で成功・失敗させる操作（レシピ削除、週コピー、複数週の再計算反映、復元）では、`autosaveEnabled` をfalseにした `ModelContext` で一連の変更を行い、1回の `save()` で確定する。
- `save()` が失敗した場合は `rollback()` を呼び、画面の状態も操作前に戻す。
- テストで保存失敗を発生させられるよう、保存処理はテスト時に失敗を注入できる形で実装する。

### 4.3 IDの一意性と関連付け
- 各モデルのIDはアプリが `UUID()` で生成する。
- IDと `weekKey` の一意性は、`@Attribute(.unique)` の動作に頼らず、保存前の処理と復元前の検証で保証する。
- `@Attribute(.unique)` を付けるかどうかは、4.1の未検証事項（重複時の動作と、復元時の置き換えへの影響）を確認してから決め、結果をユーザーに報告する。
- 削除ルールに `.cascade` を設定する場合でも、関連データの削除は削除処理で明示的に行い、自動テストで関連データが残らないことを確認する。

## 5. 日付・週の扱い
- 週はローカルカレンダーで月曜日開始とする。
- 週の識別キー `weekKey` は、月曜日のローカル日付を `yyyy-MM-dd` 形式の文字列で保存する。時刻・タイムゾーンによる週ずれを避けるため、`Date` 型を識別キーにしない。
- 日付から対象週の月曜日と `weekKey` を求める処理は独立させてテストする。
- 曜日は固定の文字列だけで保存せず、日付または安定した曜日値で管理する。

## 6. 買い物リスト再計算
- 再計算の対象週は data-design 4章の表に従って決める。対象週を求める処理はサービス層に分離してテストする。
- 再計算結果は一旦メモリ上で完成させ、成功した場合だけ保存済みスナップショットを置き換える。
- 複数週が対象の場合、全週分をメモリ上で完成させてから、全週のスナップショット置き換えと状態リセットを1回の `save()` で反映する（4.2の方針。一括性は4.1の未検証事項で、S-031で確認する）。
- 保存済みの数量を読み込んだときは data-design 3.1 の「保存値の再読み込み時の検証」を行い、不正な値は再計算の失敗として扱う。
- 失敗時は旧スナップショットと購入済み・手動削除状態を変更しない。
- 再計算が必要な状態（`needsRecalculation`）を確実に残すため、元になる変更（献立・レシピ・調味料の変更）を保存する際に、同じ `save()` で対象週の `needsRecalculation` をtrueにする。その後の再計算反映が成功したときにfalseへ戻す。
- 再計算成功後に対象週のユーザー状態をリセットする（通常の再計算）。復元時は7章に従い、状態を一律にリセットしない。
- 単位変換、表記ゆれ、調味料除外、文字数量の扱いはサービス層に分離し、テストで検証する。
- 数値数量はDecimalで計算し、途中で丸めない。表示用の丸めは表示処理でのみ行う（data-design 3.2・3.3）。
- 合算の順序を固定し、同じ入力から常に同じ値になるようにする。

## 7. バックアップ・復元
- `Codable`等を使い、バージョン付きJSON形式を定義する。数値数量はJSONの文字列型で書き出す（data-design 6章）。
- ファイル選択／保存にはiOS標準のファイル操作UIを利用する。
- 復元前にJSONをメモリ上で読み込み、形式・バージョン・ID重複・関連付けの整合性を検証する。
- ユーザー確認後、次の順で処理する。
  1. バックアップのデータから全週の買い物リストをメモリ上で再計算する。
  2. バックアップの状態を、固定キーと数量が一致する項目にだけ当てはめる。一致しなかった件数を数える。
  3. 現行データの削除、バックアップのデータの挿入、再計算したスナップショットと状態の保存を1回の `save()` で反映する。
- 1〜3のいずれかが失敗した場合は `rollback()` し、現行データを維持する。途中まで置き換えた状態を残さない。これは4.2の方針によるもので、`save()` の一括性と `rollback()` の動作は4.1の未検証事項である（B-009、D-004で確認する）。
- 数量の一致判定は、Decimalで再計算した値を正規化済み10進文字列にし、バックアップの値と完全一致で比較する。誤差を許容する比較は行わない（data-design 6章）。
- 復元に成功したら画面に成功と、復元できなかった状態の件数を表示し、必要な画面状態を更新する。

## 8. アクセシビリティと見た目
- 固定サイズの文字を必要以上に使わず、Dynamic Typeに対応する。
- ライト／ダーク両方で読みやすい標準色を使う。
- タップ領域を確保し、状態を色だけで伝えない。
- 縦向きのみをサポートする。
- 空状態とエラー状態を明確に区別する。

## 9. Git・秘密情報
- Xcodeプロジェクト、ソースコード、設計書、テストコードをGit管理する。
- ビルド生成物、ユーザーのレシピデータ、個人用バックアップ、秘密情報はコミットしない。
- `.gitignore`はXcode/Swiftの標準的な生成物を除外する内容を含める。
- Gitコミット前に差分を確認する。
