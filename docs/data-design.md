# データ設計書

## 1. 基本方針
- SwiftDataを利用し、アプリ内にローカル保存する。
- データモデルと数量計算ロジックをUIから分離する。
- 永続化操作は整合性を保つ。複数データを同時に変更する操作は一括で成功・失敗させる。
- 画面表示用の一時状態と永続化データを分ける。
- SwiftDataの具体的なモデル定義は、実際のXcodeプロジェクトとSwiftDataの制約を確認して実装する。以下は論理データモデルである。
- モデル間の参照はSwiftDataの関連付け（`@Relationship`）で表す。あわせて、各モデルはバックアップで参照できる安定したID（UUID）を保持する。
- iOS 17で利用できないAPI（例：iOS 18以降の `#Unique`、`#Index`）を前提にしない。

## 2. 論理データモデル
「関連」はSwiftDataの関連付けを表す。バックアップJSONでは関連付けを相手のIDで表す（6章）。

### Recipe
- `id`: 一意なID（UUID）
- `name`: レシピ名
- `baselineServings`: 基準人数（1〜99の整数）
- `referenceURL`: 任意の参考URL
- `notes`: 任意のメモ
- `createdAt`, `updatedAt`: 必要に応じて日時
- 関連：`ingredients`（RecipeIngredient、レシピ削除時に削除）
- 関連：`plannedDishes`（PlannedDish、レシピ削除時に削除）

### RecipeIngredient
- `id`: 一意なID（UUID）
- 関連：`recipe`（所属Recipe）
- `ingredientName`: ユーザーが入力した元の材料名（前後の半角・全角空白を除去して保存）
- `aggregationName`: 表記ゆれ解決後の集約名、または計算時に解決
- `quantityType`: `numeric` または `text`
- `numericAmount`: 数値数量。numericの場合のみ使用（0より大きく99999以下）。保存形式は3.1の「保存形式（暫定）」に従う（現時点の候補は正規化済み10進文字列。例：`"7.5"`）。計算時にDecimalとして扱う
- `textAmount`: 文字数量（例：少々、適量）。textの場合のみ使用。前後の半角・全角空白を除去して保存
- `unit`: 数値数量では必須。前後の半角・全角空白を除去し、入力した表記のまま保存する。文字数量では保存しない
- `displayOrder`: 材料表示順

### WeeklyPlan
- `id`: 一意なID（UUID）
- `weekKey`: 週の月曜日のローカル日付を `yyyy-MM-dd` 形式で表した文字列。週の識別キーで、同じ値のWeeklyPlanは1件のみ
- 関連：`dishes`（PlannedDish、WeeklyPlan削除時に削除）
- 献立登録がない週は、必ずしもレコードを作成しない

### PlannedDish
- `id`: 一意なID（UUID）
- 関連：`plan`（WeeklyPlan）
- 関連：`recipe`（Recipe）
- `weekday`: 対象曜日または日付
- `servings`: 献立上の人数（1〜99の整数）
- `displayOrder`: 同じ日の表示順

### SeasoningDictionary
- `id`: 一意なID（UUID）
- `seasoningName`: 調味料名（前後の半角・全角空白を除去して保存。辞書内で重複不可）
- `sourceType`: 初期データ／ユーザー追加を区別する値（必要に応じて）
- 初期値：「塩」「砂糖」「こしょう」「しょうゆ」「みりん」

### IngredientNameMapping
- 表記ゆれの元の材料名
- 正規化後の集約名
- 初期版ではアプリ管理で、ユーザー編集機能は設けない
- 例：「玉ねぎ」→「玉ねぎ」、「玉葱」→「玉ねぎ」
- 対応表にない名前は、元の材料名をそのまま集約キーとして使う

### ShoppingListSnapshot / ShoppingListItemState
計算結果とユーザー操作状態を分離して扱う。
- 週の識別子（`weekKey`）
- 計算結果の項目識別子（固定キー）
- 材料の集約名
- 数量種別、単位、数量、文字数量
  - 数量は合算後の内部値（表示用に丸める前の値）とし、3.1の「保存形式（暫定）」に従って保存する
- `manuallyRemoved`: 手動削除状態
- `purchased`: 購入済み状態
- `needsRecalculation`: 再計算が必要な状態（再計算失敗時などにtrue）。永続化し、アプリ再起動後も表示・再試行に使う
- 計算結果が派生データであることを踏まえ、前回正常に計算されたリストを失敗時に保持できる構成にする。
- 項目識別子は、再計算・保存を通して一貫性を保てる安定したキーとする。数量文字列だけをキーにしない。
  - 固定キーの構成：`weekKey` + 集約名 + 数量種別 + （数値数量：換算後の単位／文字数量：文字数量の文字列）
  - 数量そのものは固定キーに含めない。

## 3. 数量計算

### 3.1 入力の正規化と保存形式
数量の内部数値型はFoundationの `Decimal` とする（`Double` は使わない）。

**数値数量の入力**（次の順に処理し、どこかでエラーになった場合は保存しない）
1. 前後の半角・全角空白を除去する。
2. 全角数字（`０`〜`９`）を半角に、全角小数点「`．`」を「`.`」に変換する。ほかの全角文字は変換しない。
3. **文字数の確認**：手順2のあとの文字列の文字数が20文字以内であることを確認する。
   - 数え方：Swiftの `String.count`（書記素クラスタ単位）で数える。
   - 数字、小数点、先頭や末尾の0もすべて1文字として数える（例：`007.50` は6文字）。
   - 手順1で除去した前後の空白は数えない。
   - 20文字は入力を扱いやすい長さに抑えるための実装上の上限である。小数点以下の桁数には、この範囲内で固定の上限を設けない。
4. **形式の確認**：正規表現 `^[0-9]+(\.[0-9]+)?$` に完全一致することを確認する。一致しない入力はエラーとする。
   - 空欄、符号付き（`+1`、`-1`）、カンマ入り（`1,000`）、指数表記（`1e3`）、小数点が複数（`1..2`）、小数点の前後に数字がないもの（`.5`、`5.`）がこれに当たる。
   - macOS 13のFoundationでは、`Decimal(string:)` が `1,000` を1、`1..2` を1、`1e3` を1000、`.5` を0.5と解釈することを確認した。このため、変換の前に必ずこの形式チェックを行う。
5. **文字列での正規化**：次の規則で正規化済み10進文字列にする。
   - 整数部の先頭の0を除去する（整数部がすべて0の場合は `0` を残す）。
   - 小数部の末尾の0を除去し、小数部がなくなった場合は小数点も除去する。
   - 指数表記・桁区切りを使わない。
   - 例：`007.50` → `7.5`、`99999.000` → `99999`、`0.50` → `0.5`、`05` → `5`、`0.000` → `0`
6. **Decimalへの変換**：正規化済み文字列を、`en_US_POSIX` ロケールを指定した `Decimal(string:locale:)` でDecimalに変換する。次の場合は「数値として扱えない」エラーとする。
   - 変換結果が `nil` の場合。
   - 変換したDecimalを手順5の規則で文字列に戻した結果が、手順5の文字列と一致しない場合（Decimalで正確に表せなかった場合）。
7. **範囲の確認**：0より大きく99999以下であることを確認する（`0.000` は0なのでエラー）。
8. **保存**：手順5の正規化済み10進文字列を保存する（保存方式は下記の「保存形式」を参照）。

**保存形式（暫定）**
- 現時点では、数値数量を**正規化済み10進文字列**で保存する方式を候補とする。
  - 理由：SwiftDataのモデルにDecimal型の属性を持たせて、精度を保ったまま保存・読み込みできるかは、iOS 17で未検証である（technical-design 4.1）。文字列であれば、保存・読み込みで値が変わらない。
- SwiftDataにDecimalを直接保存する方式と、文字列で保存する方式の両方を、第1段階でiOS 17シミュレーターで検証する（D-006）。結果を見てから保存形式を確定する。
- 採用した方式、その理由、検証結果は technical-design 4.4 に記録する。

**保存値の再読み込み時の検証**
- 保存済みの数値数量を読み込んで計算に使うときは、手順4（形式）、手順5の規則で正規化済みであること、手順6（Decimalへの変換）、手順7（範囲）を再度確認する。保存時に確認済みでも省略しない。
- 買い物リストの保存済み数量（再計算結果）も、手順4・5・6で確認する。再計算の結果なので、20文字の上限と範囲の確認は適用しない。
- 不正な値を見つけた場合は、推測で修正したり0として扱ったりしない。その計算は失敗として扱い、4章の「再計算の失敗」と同じく旧リストと状態を保持し、エラーを表示する。
- 不正な値を含むレシピをS-03で開いた場合も、保存されている値は変更しない。正しい値が入力され、S-03の保存操作で入力チェックに通るまで、そのRecipeIngredientを含むレシピのデータ（ほかの材料を含む）を更新しない。キャンセル時は元のデータを保持する（screen-design §4、テスト R-021〜R-025）。
- 不正な値の検出を理由に、ほかの正常な材料、レシピ、献立、買い物リストのデータを変更しない。

**人数の入力**（基準人数・献立人数）
- 前後の空白を除去し、全角数字を半角に変換する。
- 正規表現 `^[0-9]{1,2}$` に一致し、値が1〜99であることを確認する。
- 先頭の0は受け付ける（例：`05`、`０５` → 5）。`0`、`00` は範囲外としてエラーにする。

### 3.2 計算
1. 献立の各料理について、数値数量は `材料数量 × 献立人数 ÷ レシピ基準人数` の順（乗算のあとに除算）でDecimalで計算する。文字数量は倍率計算しない。
2. アプリは計算の途中で丸めを行わない。
3. **Decimalの精度について**
   - Decimalの有効数字は最大38桁で、これを超える計算結果（例：1÷3）は打ち切られる。macOS 13のFoundationでは、1÷3を3回足すと `0.99999999999999999999999999999999999999` になることを確認した（表示時の丸めで「1」になる）。
   - 入力を20文字以内に制限しても、計算精度が保証されるわけではない。乗算・除算・合算を重ねた結果の精度は、自動テスト（S-024、S-036〜S-039）でiOS 17上で確認する。
   - 精度が足りないケースが見つかった場合は、ユーザーに報告して計算方式を見直す。
4. 合算は、同じ入力から常に同じ値になるよう固定の順序で行う。順序は、曜日（月→日）、料理の表示順、材料の表示順とする。
5. 換算倍率（kg→g、L→ml）は ×1000、cc→ml は ×1 で、Decimalで計算する。

### 3.3 表示
**表示ルール**：最終的な合算結果を小数第2位に四捨五入し、末尾の0を省略する。正の値が丸めによって0になる場合は「0.01未満」と表示する。

- 「最終的な合算結果」とは、3.4の手順で集約した後の値である。個々の料理の値を先に丸めない（例：0.004を3つ合算すると0.012なので「0.01」と表示する）。
- 四捨五入は `NSDecimalRound`（scale 2、丸めモード `.plain`）で行う。macOS 13のFoundationでは、0.125 → 0.13、0.124 → 0.12、2.005 → 2.01、0.004 → 0 となることを確認した。iOS 17での動作は自動テスト（S-034、S-035）で確認する。
- 末尾の0と、不要になった小数点を省く（1.50 → 1.5、2.00 → 2）。
- 桁区切りは使わない（例：1500g）。

### 3.4 集約手順
1. 各料理の必要量を3.2で計算する。
2. 調味料辞書に完全一致する材料を除外する。照合には入力された元の材料名（`ingredientName`、前後空白除去済み）を使い、表記ゆれ対応表で統一した後の集約名は使わない。全角・半角の変換や大文字・小文字の同一視は行わない。類似名を自動除外しない。
   - 例：辞書に「しょうゆ」だけがある場合、「醤油」は除外しない。対応表で「醤油」の集約名が「しょうゆ」になる場合でも除外しない。
3. 材料名の表記ゆれ対応表を適用して集約名を決める。
4. 既知単位を換算する。単位（前後空白除去済み）が次の定義済み表記と完全一致する場合だけ換算する。
   - `g`、`kg`、`ｇ`、`ｋｇ` → g（kgは×1000）
   - `ml`、`mL`、`L`、`l`、`cc`、`ｍｌ`、`ｍＬ`、`Ｌ`、`ｌ`、`ｃｃ` → ml（L・lは×1000、ccは×1）
   - 上記以外（`KG`、`ML`、`CC`、`Kg` などの大文字・混在表記、カタカナ表記を含む）は換算しない。
5. 同じ集約名、同じ数量種別、同じ単位（換算後）の数値数量を集約する。換算対象外の単位は単位文字列の完全一致でのみ集約する。
6. 互換性のない単位は別数量として保持する。
7. 文字数量は数値に変換せず、別項目として保持する。同じ集約名で同じ文字数量（前後空白除去済みの完全一致）のものは1項目にまとめ、異なる文字数量は別項目とする。
8. 表示時のみ3.3の表示ルールに従って丸める。

## 4. 状態更新ルール
次の変更があった場合、対象週の買い物リストを再計算する。影響しない週は再計算しない。

| 変更 | 対象週 |
|---|---|
| 献立料理の追加・削除 | その週 |
| 献立人数の変更 | その週 |
| 週コピー | コピー先の週 |
| レシピ材料の追加・編集・削除 | そのレシピを使う全週（過去の週を含む） |
| レシピ基準人数の変更 | そのレシピを使う全週 |
| レシピ削除 | 削除前にそのレシピを使っていた全週 |
| 調味料の追加・削除 | その調味料名と完全一致する材料名を含む週 |
| レシピ名・メモなど材料数量に影響しない項目のみの変更 | 再計算しない |

- 通常の再計算が成功した場合、対象週の手動削除・購入済み状態をリセットする。
- 複数週が対象の場合、全週の再計算結果を一括で反映する。
- 再計算が失敗した場合、対象全週の前回の計算結果と状態を維持し、`needsRecalculation` を保存して古い可能性を表示し、再試行できるようにする。
- バックアップ復元時の再計算は通常の再計算と区別する（状態を一律にリセットしない。5章・6章）。

## 5. 削除・トランザクション
- レシピ削除：Recipe、RecipeIngredient、関連する全PlannedDishを一括削除する。失敗時は全体をロールバックする。
- 週コピー：コピー先の既存献立を置き換える場合、確認後に一括更新する。コピー元は変更しない。
- 復元：データ検証後に、データの置換、全週の再計算、状態の復元を一括で行う。いずれかが失敗した場合は全体を取り消し、現行データを保持する。
  - 状態の復元：バックアップの状態のうち、再計算後のリストに同じ固定キーの項目があり、かつ数量がバックアップ時点の数量と一致するものだけを復元する（照合方法は6章）。
  - 復元できなかった状態の件数を復元結果として表示する。復元できない状態があっても復元の失敗とはしない。
- 設定保存失敗時は旧設定を維持する。
- 上記の一括処理を実現する方法（SwiftDataの `save()`／`rollback()`）と、その動作が未検証であることは technical-design 4.1・4.2 に記載する。

## 6. バックアップJSON
JSONのトップレベルに少なくとも以下を含める。
- `formatVersion`
- `exportedAt`
- `recipes`
- `recipeIngredients`（またはレシピ内にネストした材料）
- `weeklyPlans`
- `plannedDishes`
- `seasoningDictionary`
- `ingredientNameMappings`
- `shoppingListStates`

日時はISO 8601形式など一貫した形式で保存する。IDと参照関係を維持する。関連付けは相手のUUIDで表す（例：PlannedDishの `recipeID`、`planID`）。

`shoppingListStates` の各要素には、`weekKey`、固定キー、状態を付けた時点の数量（数値数量の値、または文字数量）、`manuallyRemoved`、`purchased` を含める。計算結果のスナップショット本体と `needsRecalculation` は派生データのため含めず、復元時に再計算する。

**数値の書き出し形式**：数値数量（材料の `numericAmount` と、状態の数量）は、JSONの数値型ではなく、3.1の正規化済み10進文字列（JSONの文字列型）で書き出す。JSONの数値型とDecimalの相互変換で精度が保たれるかはiOS 17で未検証であり、端末やOSバージョンに依存させないためである。この形式は、SwiftDataでの保存形式（3.1の「保存形式（暫定）」）がどちらに決まっても変えない。

**復元時の数量照合**：
1. 材料の数量を3.1の手順3〜7（文字数、形式、正規化済みであること、Decimalへの変換、範囲）で検証する。正規化済みでない値（例：`"7.50"`）は、書き出し時の形式と異なるため不正として拒否する。
2. 3.2・3.4の手順で全週の買い物リストを再計算する。
3. 再計算した各項目の数量を3.1の正規化規則で10進文字列にする。
4. バックアップの状態の数量（正規化済み10進文字列）と、手順3の文字列を完全一致で比較する。誤差を許容する比較は行わない（例：38桁目だけが異なる値は一致としない）。文字数量の項目は、固定キーに文字数量が含まれるため、固定キーの一致で照合する。
5. 一致した状態だけを復元し、一致しなかった件数を数える。

復元時は、必須フィールド、型、ID重複、参照先の存在（関連付けの整合性）、`weekKey` の形式と重複、1〜99の人数、材料の数量（3.1の手順3〜7）、状態の数量（3.1の手順4〜6。再計算値のため20文字の上限と範囲の確認は適用しない）、数量がJSONの文字列型であることなどを検証する。未知の非対応バージョンは拒否し、現行データを変更しない。

**復元に失敗した場合**：検証エラー、再計算の失敗、保存の失敗のいずれでも、現行データ（レシピ、材料、献立、調味料辞書、表記ゆれ対応表、買い物リストと購入済み・手動削除状態、`needsRecalculation`）を一切変更しない。これをどう実現するかと、その未検証事項は technical-design 4.1・4.2 に記載する。

## 7. 初期データ
初期調味料辞書として「塩」「砂糖」「こしょう」「しょうゆ」「みりん」を登録する。サンプルレシピは登録しない。初期データの投入が複数回実行されても重複登録しない。
