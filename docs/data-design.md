# データ設計書

## 1. 基本方針
- SwiftDataを利用し、アプリ内にローカル保存する。
- データモデルと数量計算ロジックをUIから分離する。
- 永続化操作は整合性を保つ。複数データを同時に変更する操作は一括で成功・失敗させる。
- 画面表示用の一時状態と永続化データを分ける。
- SwiftDataの具体的なモデル定義は、実際のXcodeプロジェクトとSwiftDataの制約を確認して実装する。以下は論理データモデルである。

## 2. 論理データモデル

### Recipe
- `recipeID`: 一意なID
- `name`: レシピ名
- `baselineServings`: 基準人数（正の整数）
- `referenceURL`: 任意の参考URL
- `notes`: 任意のメモ
- `createdAt`, `updatedAt`: 必要に応じて日時

### RecipeIngredient
- `ingredientID`: 一意なID
- `recipeID`: 所属レシピID
- `ingredientName`: ユーザーが入力した元の材料名
- `aggregationName`: 表記ゆれ解決後の集約名、または計算時に解決
- `quantityType`: `numeric` または `text`
- `numericAmount`: 数値数量。numericの場合のみ使用
- `textAmount`: 文字数量（例：少々、適量）。textの場合のみ使用
- `unit`: 数値数量では必須。文字数量では必要に応じて保存
- `displayOrder`: 材料表示順

### WeeklyPlan
- `planID`: 一意なID
- `weekStartDate`: 週の月曜日の日付。週の識別キー
- 献立登録がない週は、必ずしもレコードを作成しない

### PlannedDish
- `plannedDishID`: 一意なID
- `planID`: WeeklyPlan ID
- `recipeID`: Recipe ID
- `weekday`: 対象曜日または日付
- `servings`: 献立上の人数（正の整数）
- `displayOrder`: 同じ日の表示順

### SeasoningDictionary
- `seasoningID`: 一意なID
- `seasoningName`: 調味料名
- `sourceType`: 初期データ／ユーザー追加を区別する値（必要に応じて）
- 初期値：「塩」「砂糖」「こしょう」「しょうゆ」「みりん」

### IngredientNameMapping
- 表記ゆれの元の材料名
- 正規化後の集約名
- 初期版ではアプリ管理で、ユーザー編集機能は設けない
- 例：「玉ねぎ」→「玉ねぎ」、「玉葱」→「玉ねぎ」
- 対応表にない名前は、元の材料名をそのまま集約キーとして使う

### ShoppingListSnapshot / ShoppingListItemState
計算結果とユーザー操作状態を分離して扱う。
- 週の識別子
- 計算結果の項目識別子
- 材料の集約名
- 数量種別、単位、数量、文字数量
- `manuallyRemoved`: 手動削除状態
- `purchased`: 購入済み状態
- 計算結果が派生データであることを踏まえ、前回正常に計算されたリストを失敗時に保持できる構成にする。
- 項目識別子は、再計算・保存を通して一貫性を保てる安定したキーとする。数量文字列だけをキーにしない。

## 3. 数量計算
1. 献立の各料理について、材料数量 ×（献立人数 ÷ レシピ基準人数）で必要量を計算する。
2. 数値は内部計算で途中丸めしない。
3. 材料名の表記ゆれ対応表を適用して集約名を決める。
4. 調味料辞書に完全一致する材料を除外する。照合は正規化後の集約名に対して行うか元名に対して行うかを一貫して実装し、初期値・表記ゆれとの整合をテストで確認する。仕様としては調味料名の完全一致を前提とし、類似名を自動除外しない。
5. 同じ集約名、同じ数量種別、互換単位の数値数量を集約する。
6. g/kgはg、ml/Lはmlへ換算する。
7. 互換性のない単位は別数量として保持する。
8. 文字数量は数値に変換せず、別項目として保持する。
9. 表示時のみ小数第2位までに丸める。

文字数量が複数ある場合は誤って数値合算しない。元の表現を区別して表示する。具体的な表示形式は実装時にUI案を提示し、必要ならユーザーに確認する。

## 4. 状態更新ルール
次の変更があった場合、該当週の買い物リストを再計算する。
- 献立料理の追加・削除
- 献立人数の変更
- レシピ材料の追加・編集・削除
- レシピ削除
- 調味料辞書の変更
- 週コピー

再計算が成功した場合、該当週の手動削除・購入済み状態をリセットする。
再計算が失敗した場合、前回の計算結果と状態を維持し、古い可能性を記録・表示して再試行できるようにする。
レシピ名・メモなど材料数量に影響しない編集は、必要以上のリスト再計算を避けてもよい。ただし表示に影響する場合は整合性を保つ。

## 5. 削除・トランザクション
- レシピ削除：Recipe、RecipeIngredient、関連する全PlannedDishを一括削除する。失敗時は全体をロールバックする。
- 週コピー：コピー先の既存献立を置き換える場合、確認後に一括更新する。コピー元は変更しない。
- 復元：データ検証後に一括置換し、失敗時は現行データを保持する。
- 設定保存失敗時は旧設定を維持する。

## 6. バックアップJSON
JSONのトップレベルに少なくとも以下を含める。
- `formatVersion`
- `exportedAt`
- `recipes`
- `recipeIngredients`（またはレシピ内にネストした材料）
- `weeklyPlans`
- `plannedDishes`
- `seasoningDictionary`
- `ingredientNameMappings`
- `shoppingListStates`

日時はISO 8601形式など一貫した形式で保存する。IDと参照関係を維持する。復元時は、必須フィールド、型、ID重複、参照先の存在、正の人数・数量などを検証する。未知の非対応バージョンは拒否し、現行データを変更しない。

## 7. 初期データ
初期調味料辞書として「塩」「砂糖」「こしょう」「しょうゆ」「みりん」を登録する。サンプルレシピは登録しない。初期データの投入が複数回実行されても重複登録しない。
