# 要件定義書：週間献立・買い物リストアプリ

## 1. 目的
手動登録したレシピを使って1週間（月曜日〜日曜日）の夕食献立を管理し、登録された料理と人数から材料の必要量を集計した買い物リストを作成する。まず個人利用できる状態を完成させ、一般公開は完成後に検討する。

## 2. 対象環境・基本方針
- iPhone専用、iOS 17以降。
- Swift、SwiftUI、SwiftDataを使用する。
- 縦向き画面のみ、日本語UIのみ。
- iPhoneの外観設定に従ってライト／ダークモードを切り替える。
- Dynamic TypeなどiPhoneの文字サイズ設定に対応し、大きな文字でもレイアウトが破綻しないようにする。
- 献立・レシピ・買い物リストなどの主要機能はオフラインで動作する。
- レシピの参考URLは保存できるが、URL先の閲覧にはインターネットが必要。
- ログイン、サーバー、クラウド同期、広告、分析、利用状況や個人データの外部送信は実装しない。
- データは端末内に保存する。アンインストールでデータが消える可能性を許容し、必要に応じてユーザーがJSONバックアップを作成する。自動バックアップは行わない。
- 普段の操作で快適に応答すること。数値での性能目標は設けず、実機で確認する。

## 3. 機能要件

### 3.1 レシピ管理
レシピには次を登録する。
- レシピ名（必須）
- 基準人数（必須、1〜99の整数）
- 材料名、数量、単位
- 参考URL（任意）
- メモ（任意）

同じ名前のレシピを複数登録できる。重複レシピ名や同じレシピ内の重複材料を禁止しない。材料が0件でもレシピを登録でき、後から材料を追加できる。

入力チェック:
- レシピ名は空白のみを不可とする。
- 基準人数は1〜99の整数。全角数字は半角に変換して受け付ける。先頭の0は受け付ける（「05」「０５」は5）。
- 入力された材料行の材料名は必須。材料名は前後の半角・全角空白を除去して保存する。
- 数値数量は0より大きく99999以下の小数を許可する。空欄、0、負数、99999超、カンマ入り（例：「1,000」）、数値として解釈できない入力は不可。全角数字と全角小数点「．」は半角に変換して受け付ける。「.5」「5.」のように小数点の前後に数字がない入力は不可。小数点以下の桁数に固定の上限は設けないが、実装上の上限として入力は20文字以内とする（数え方と処理順はデータ設計書3.1）。
- 数値数量の単位は必須。単位は自由入力とし、前後の半角・全角空白を除去したうえで、入力した表記のまま保存する。
- 「少々」「適量」などの文字数量は空欄不可。前後の半角・全角空白を除去して保存する。文字数量の場合は単位を入力・保存しない。
- 参考URLは任意。入力時はURL形式を検証する。
- メモは任意。
- エラーは該当項目の近くに表示し、入力内容を保持する。

編集時は、保存済みの献立に使用されているレシピも直ちに更新内容を反映する。

保存されている数量が不正な材料（データ設計書3.1の「保存値の再読み込み時の検証」で不正と判定されたもの）を含むレシピを編集画面で開いた場合:
- 不正な材料の行にエラーを表示し、どの項目が不正か分かるようにする。
- 不正な値を推測で補正したり、0に置き換えたりしない。
- ユーザーが正しい値を再入力できるようにする。
- 正しい値を入力して保存するまでは、元のデータを変更しない。編集をキャンセルした場合も元のデータを保持する。
- 不正な材料があることを理由に、ほかの正常な材料やレシピのデータを変更しない。

レシピ削除時は確認ダイアログを表示する。確定した場合、レシピ本体、材料、および全週のそのレシピを参照する献立登録を削除する。週の献立自体は残す。削除に失敗した場合はすべてを取り消し、元のデータを保持する。献立から料理を削除する操作は、レシピ自体を削除しない。

### 3.2 週間献立
- 1週間は月曜日〜日曜日で、各日の夕食を管理する。
- 1日に複数の料理を無制限に登録できる。
- 献立に登録した料理ごとに人数を指定する。人数は1〜99の整数。全角数字は半角に変換して受け付ける。先頭の0は受け付ける（「05」「０５」は5）。
- 前週／翌週へ移動できる。
- 週は月曜日の日付を基準に識別する。識別キーはローカル日付の `yyyy-MM-dd` 形式とする。
- 献立登録がない週は、週データを事前に保存する必要はない。
- レシピ一覧から料理を選んで献立に追加する。
- 週間献立画面にレシピボタンを常設し、いつでもレシピ一覧（管理）へ移動できる。
- 料理の並び順を保持する。
- 別の週の献立を、表示中の週へコピーできる。コピー先は表示中の週に固定し、ユーザーはコピー元の週だけを選ぶ。コピー元の初期値は前週。曜日、料理、人数、並び順をコピーし、独立した献立登録を作る。コピー元は変更しない。
- コピー元の週に献立がない場合、またはコピー元とコピー先が同じ週の場合はコピーを実行できない。
- コピー先に献立がある場合、置き換える前に確認する。承認した場合に限りコピー先の週全体を置き換える。キャンセル時はコピー先を変更しない。
- 週コピー後は買い物リストを再計算し、手動削除・購入済み状態をリセットする。
- 初回起動時は現在の週を表示し、サンプルレシピは登録しない。

### 3.3 買い物リスト
- 選択した週の献立と人数をもとに、材料の必要量を計算する。
- 調味料辞書に完全一致する材料は買い物リストから除外する。
- 初期調味料は「塩」「砂糖」「こしょう」「しょうゆ」「みりん」。
- 調味料名の追加・削除ができる。調味料名は前後の半角・全角空白を除去して保存する。空欄（空白のみを含む）・重複名は不可。
- 調味料判定は、入力された材料名（前後空白除去後）と調味料名の完全一致とする。材料名の表記ゆれ対応（集約用の表記統一）とは別の処理であり、対応表で統一した後の名前では判定しない。「しょうゆ」と「醤油」は別の名前として扱う。必要なら両方を登録する。全角・半角の変換や大文字・小文字の同一視は行わない。
- 明らかな表記ゆれはアプリ内の対応表で正規化する（例：「玉ねぎ」「玉葱」）。ユーザーが編集する機能は初期版では設けない。対応表にない材料は完全一致で集約する。
- 同じ正規化材料名・同じ単位の数値数量は合算する。
- 既知単位は計算時に換算する。入力した単位表記は変更せずに保存する。
  - `g`、`kg` とその全角表記（`ｇ`、`ｋｇ`）は g に換算する。
  - `ml`、`mL`、`L`、`l`、`cc` とその全角表記（`ｍｌ`、`ｍＬ`、`Ｌ`、`ｌ`、`ｃｃ`）は ml に換算する。
  - 既知単位は上記の定義済み表記（前後空白除去後）との完全一致でのみ認識する。`KG`、`ML`、`CC`、`Kg` などの大文字・混在表記や、カタカナ表記（例：「グラム」「リットル」）は自動換算の対象外とし、単位の完全一致でのみ合算する。
- 互換性のない単位（例：玉ねぎ2個と玉ねぎ200g）は同じ材料の見出し配下に表示しても、数量は別々に保持し、相互換算しない。
- 「少々」「適量」などの文字数量は数値として合算しない。人数による倍率計算も行わない。同じ材料の同じ文字数量はまとめて1つ表示し、異なる文字数量は区別して表示する。
- 数量の内部数値型はDecimalとする。アプリは計算の途中で丸めない。Decimalの精度上限（有効数字38桁）を超える結果は打ち切られるため、計算精度はテストで確認する（データ設計書3.2）。
- 表示は、最終的な合算結果を小数第2位に四捨五入し、末尾の0を省略する。正の値が丸めによって0になる場合は「0.01未満」と表示する（例：1.50 → 1.5、2.00 → 2、0.004 → 0.01未満）。個々の料理の値を先に丸めない。
- 材料ごとの個数から重量への換算など、換算データがない単位変換はしない。
- 買い物リスト項目を手動で削除できる。これはレシピを変更しない。
- 購入済みチェックを付けられる。
- 献立、人数、レシピ材料、調味料辞書の変更などでリストを再計算した場合、対象週の手動削除状態と購入済み状態はリセットされる。削除した材料は再計算後に再表示される。
- 再計算の対象週は次のとおりとし、影響しない週は再計算しない。
  - 献立料理の追加・削除、献立人数の変更、週コピー：その週。
  - レシピ材料の追加・編集・削除、基準人数の変更、レシピ削除：そのレシピを使う全週（過去の週を含む）。
  - 調味料の追加・削除：その調味料名と完全一致する材料を含む週。
  - レシピ名・メモなど材料数量に影響しない項目のみの変更：再計算しない。
- 複数週が対象の場合、全週の再計算結果を一括で反映する。一部の週だけが更新された状態を残さない。
- 買い物リストを再度開いただけで再計算が発生しない場合、手動削除状態と購入済み状態を維持する。
- 再計算に失敗した場合は、前回のリストと状態を保持し、古い可能性があることを表示し、再試行できるようにする。成功するまでは新しいリストへ置き換えない。再計算が必要な状態は保存し、アプリ再起動後も表示・再試行できるようにする。
- バックアップ復元時の再計算は通常の再計算と区別し、状態を一律にリセットしない（3.4参照）。

### 3.4 バックアップ・復元
- JSON形式で手動バックアップ・復元する。
- バックアップ対象：レシピ、材料、週間献立、献立人数と順序、調味料辞書、材料名表記ゆれ対応表、買い物リストの手動削除状態・購入済み状態。
- JSONにはデータ形式バージョンを含める。
- 一時的な画面状態は含めない。
- iOSのファイル選択UIでユーザーが保存先を選ぶ。
- 復元時は選択ファイルの形式、バージョン、データ整合性を検証し、既存データを置き換える旨を確認する。
- キャンセル時は変更しない。
- 復元時は選択ファイルのIDの重複と参照関係（関連付け）の整合性を検証する。
- 復元では、データの置き換え、全週の買い物リスト再計算、購入済み・手動削除状態の復元を一連の処理として行う。
  - 状態は、買い物リスト項目の固定キーと数量がバックアップ時点と一致する項目にのみ復元する。
  - 一致しないため復元できなかった状態の件数を、復元結果としてユーザーに知らせる。これは復元の失敗とはしない。
  - 再計算に失敗した場合は復元全体を取り消し、現行データを変更しない。
- 復元は一括で実行し、失敗時や不正ファイル時は現行データを変更しない。
- CSV出力は対象外。
- バックアップ作成失敗時はアプリデータを変更せず、エラー表示と再試行を可能にする。

### 3.5 保存・起動・エラー対応
- 保存失敗時はエラーを表示し、入力内容を可能な限り保持して再試行できるようにする。部分的な保存を避ける。
- 設定の保存に失敗した場合は以前の設定を維持する。
- 編集中にアプリが予期せず終了した場合、最後に保存された状態から再開する。未保存の下書き自動復旧は初期版の対象外。
- 起動時のデータ読み込みに失敗した場合、空データとして初期化したり既存データを上書きしたりしない。エラー表示、再試行、バックアップからの復元導線を提供する。
- 買い物リストの再計算失敗時は前回のリストと状態を保持し、古い可能性を明示して再試行可能にする。
- データの削除や復元は一部だけ反映されないようにする。

## 4. 画面一覧
- S-01 週間献立：週表示、前週／翌週、曜日ごとの料理、料理追加・削除、人数変更、買い物リストへの遷移、献立コピー、レシピボタン（常設）。
- S-02 レシピ一覧：管理モード（閲覧、追加、編集、削除）と選択モード（献立へ追加するレシピの選択、レシピ追加。編集・削除は不可。選択モードで新規登録したレシピは献立へ自動追加しない）。
- S-03 レシピ登録・編集：レシピ名、基準人数、材料行、数量種別、数量、単位、参考URL、メモ、保存・キャンセル。
- S-04 買い物リスト：集約材料・必要量、手動削除、購入済みチェック、再計算エラー表示と再試行。
- S-05 設定：調味料辞書の編集、バックアップ・復元、アプリ情報。
- S-06 バックアップ・復元：JSONの書き出し・選択、復元確認、処理結果表示。

## 5. 初回起動と空状態
- 初回起動時は現在の週の週間献立を表示する。
- サンプルデータは作らない。
- レシピが0件の場合、「レシピを登録する」導線を表示する。
- レシピが存在しても選択週に献立がない状態と、材料がないため買い物リストが空の状態を区別して説明する。
- レシピをすべて削除した場合も、登録案内を表示する。

## 6. 非機能要件
- iOS 17以降、iPhoneのみ、縦向き、日本語UI。
- ダークモードとDynamic Typeに対応する。
- コア機能はオフライン対応。
- 個人データや利用状況を外部送信しない。広告・分析機能なし。
- 通常利用で快適な応答性を保ち、実機で確認する。
- App Store公開は初期開発の完了後に検討する。

## 7. 開発・品質方針
- 基本機能から段階的に実装する。
- Gitで変更履歴を管理し、動作確認済みの区切りでコミットする。
- 要件・設計変更は、理由と影響範囲を提示してユーザーの承認を得てから行う。
- 自動テストと手動テストを組み合わせ、iOSシミュレーターと実機iPhoneで確認する。
- 定義したすべてのテスト項目が成功するまで、テスト完了・公開準備完了と判断しない。
